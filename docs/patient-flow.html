OPSAmple — Patient Journey & Data Flow

v2 · Target architecture annotated with what exists in code today (repo: OPSAmplehtml, verified 2026-08-04). Scheduling = local site’s team; Sevaro Desktop Scribe shown as a candidate note surface.
#DATA FLOWSTATUSWHERE IT LIVES
1Referral / patient info → TriageLIVETriageInputPanel.tsx (paste/upload) → /api/triage. Fax/OCR ingester (infrastructure/triage-ingestion) built, not deployed. No partner-facing API yet.
2Triage → Local schedulersHUMAN + ASSISTBooking is the partner site’s own scheduling team, guided by triage tier/routing. Code assist exists: autoSchedule.ts auto-drafts a pending-review appointment for the urgent tier.
3Triage → HistorianLIVEcontextBuilder.ts — historian opens pre-briefed with chief complaint, red flags, tier. This is the Mayo demo path, end-to-end.
4Referral note → note engineLIVEreport-builder.ts — report’s first section is built from the triage/referral data.
5Historian → note engineLIVE ×2Feeds both pipelines: consult report (report-builder.ts) and signed note (import-historian API → HPI/ROS/history). The two pipelines themselves aren’t bridged.
6SENSE exam → signed notePLANNEDAuto-links into consult report + historian context today (postMessage). Import into the signed /ehr note is scoped in the SENSE integration plan.
7Signed note → Follow-up agentLIVEsign/route.ts → triggerFollowUpFromVisit() — fires automatically on signing, non-blocking.
8Visit → RPMPLANNEDRPM data fully isolated today (own DB, read-only dashboards). Enrollment + monitoring loop scoped in the Outpatient RPM plan.
9Desktop Scribe → signed noteOPTIONSevaro Desktop Scribe as the dictation surface for the visit — separate product today; integration approach TBD.
