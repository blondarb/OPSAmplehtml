## ⚠️ Correction to carry forward: multi-document IS built

I twice told Steve multi-file upload "was never built". **Wrong.** The evidence:

- `longPacketPlanner` takes `documents: LongPacketSourceDocument[]` with `packetId`,
  **`expectedDocumentCount`**, `documentId`, `documentOrder`, per-document page provenance
- `runLongPacketModelPipeline` is **called live** at `extract/route.ts:1282` — big PDFs really
  are chunked, page-mapped and emergency-screened
- The route hard-codes `documentId: 'document-1'` (~line 979), and the intake rejects
  `fileParts.length !== 1`

So: **the engine is multi-document; the intake was narrowed to one file** by the source-bound
extraction work (`293e828`) — the same change Steve noticed as "when did we start doing
source-bound extraction?". Not absent. Fenced off.

Also found: `LONG_PACKET_REQUIRED` is handled (413) but **thrown nowhere**, and above
`MAX_INLINE_LONG_PACKET_CHUNKS = 80` the route safely parks the packet pending a durable
worker (`TRIAGE_LONG_PACKET_DURABLE_ENABLED`, not set on prod). That is the 200-page path.

**Reconnecting, in order:** accept N files at intake → build one `LongPacketSourceDocument`
per file instead of the literal → extend source-bound approval to approve a *packet* (the real
work, and the clinical crux) → stand up the durable worker for 200-page packets.
